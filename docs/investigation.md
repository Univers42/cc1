Architectural Design and Engineering Specifications for a Data-Oriented C89 Compiler in RustThe development of a C compiler is a multifaceted engineering endeavor that intersects formal language theory, computer architecture, and high-performance software design. In the context of modern systems programming, the Rust programming language offers a unique set of abstractions that allow for memory safety without sacrificing the low-level control required for efficient translation. This report provides a comprehensive technical framework for the construction of a C89-compliant compiler (cc1) and its corresponding driver (fcc), emphasizing original architecture inspired by the Static Single Assignment (SSA) paradigms of modern toolchains while strictly adhering to the ANSI X3.159-1989 standard and the System V Application Binary Interface (ABI) for both i386 and x86_64 architectures.A central pillar of this design is the adoption of Data-Oriented Design (DOD), which prioritizes memory layout and cache locality over traditional object-oriented hierarchies. By utilizing handle-based AST structures and arena-allocated memory, the implementation seeks to achieve superior compilation speeds. Furthermore, the project incorporates a full metaprogramming preprocessor and comprehensive DWARF debugging support via LLVM metadata, ensuring a professional-grade toolchain suitable for complex software ecosystems.Theoretical Foundations: The ANSI C89 Standard and Translation PhasesThe C89 standard established the conceptual model for C translation, defining a rigorous sequence of transformations that convert physical source files into an executable program image. A robust compiler implementation must distinguish between the translation environment and the execution environment, respecting the environmental limits and numerical constraints imposed by the target architecture.Detailed Breakdown of Translation Phases 1 through 4The preprocessor represents the first four phases of translation. Compliance requires a recursive mechanism that handles file inclusion and macro expansion with strict adherence to precedence rules.PhaseTechnical RequirementMechanism of ImplementationPhase 1Multibyte Mapping and TrigraphsPhysical source characters are mapped to the source character set. Trigraphs (e.g., ??=) are replaced by internal representations (e.g., #).Phase 2Line SplicingBackslash-newline sequences are deleted, merging physical lines into logical ones. A source file must end in a newline not preceded by a backslash.Phase 3Tokenization and Comment StripThe source is decomposed into preprocessing tokens. Comments are replaced by a single space character. Newlines are preserved.Phase 4Directive Execution and Macro ExpansionPreprocessing directives (#include, #define, #if) are executed. Macro invocations are expanded recursively.The implementation of Phase 4 is particularly complex, as it necessitates a symbol table for macros and a state machine for conditional inclusion. The standard requires that a #include directive triggers Phases 1 through 4 on the named header file recursively. After Phase 4, all preprocessing directives are deleted, leaving a flattened stream of tokens ready for syntactic analysis.Lexical Elements and "Maximal Munch"In Phase 3, the compiler must implement the "Maximal Munch" rule, which dictates that the next preprocessing token is the longest sequence of characters that could constitute a token. This prevents ambiguity in operators like ++ and +=. For example, x+++++y is always parsed as x ++ ++ + y, which results in a syntax error because x++ produces an r-value that cannot be incremented again. The lexical analyzer, developed via the custom ft_lex tool, must categorize tokens into keywords, identifiers, constants, string literals, operators, and punctuators.Architectural Binary Interface: i386 vs. x86_64 ComplianceA core requirement of this compiler is support for cross-compilation. The program must maintain absolute consistency in structure offsets, alignments, and constant expression evaluations across the Intel386 and AMD64 targets. This requires the compiler to be "target-aware" during every phase of semantic analysis and code generation.Scalar Type RepresentationsThe numerical representation of fundamental types varies significantly between the 32-bit i386 and 64-bit x86_64 models, specifically under the LP64 data model utilized by System V x86_64.Scalar Typei386 Size (Bytes)i386 Alignmentx86_64 Size (Bytes)x86_64 Alignment_Bool1111char1111short2222int4444long4488long long8488pointer4488float4444double8488long double1241616The discrepancy in long sizes is the most common source of portability errors. On i386, unsigned long is a 32-bit value, whereas on x86_64, it is 64-bit.Compile-Time Constant Evaluation SemanticsThe requirement for consistent constant expression evaluation is illustrated by the handling of the bitwise complement and modulo operators on unsigned long. Consider the expression: enum e { A = ~(unsigned long int)1 % 7 };.On i386 (32-bit):(unsigned long int)1 is 0x00000001.~(unsigned long int)1 is 0xFFFFFFFE (4,294,967,294).4294967294 % 7 results in 2.On x86_64 (64-bit):(unsigned long int)1 is 0x0000000000000001.~(unsigned long int)1 is 0xFFFFFFFFFFFFFFFE (18,446,744,073,709,551,614).18446744073709551614 % 7 results in 0.The compiler's constant folder must utilize the precision of the target architecture, not the host architecture, to ensure that these enums and static initializers are evaluated correctly.Aggregates and Alignment RulesThe System V ABI mandates that structures and unions assume the alignment of their most strictly aligned component. Each member is assigned to the lowest available offset consistent with its alignment requirements. This often necessitates internal padding.For a structure defined as struct { char a; double b; int c; }:i386 Layout: a at 0, 3 bytes padding, b at 4 (i386 only requires 4-byte alignment for doubles), c at 12. Total size: 16.x86_64 Layout: a at 0, 7 bytes padding, b at 8 (requires 8-byte alignment), c at 16. Total size: 24.The cc1 compiler must implement a target-specific layout engine that calculates these offsets during semantic analysis to provide correct values for the sizeof operator and pointer arithmetic.High-Performance Frontend: Data-Oriented Design in RustTraditional compiler architectures often represent the Abstract Syntax Tree (AST) as a recursive structure of pointers (e.g., Box<Node> or Rc<Node>). While idiomatic in many high-level languages, this "object spiderweb" causes significant performance degradation due to heap fragmentation and cache misses during tree traversals.Handle-Based AST and Vector StorageTo prioritize speed and structural integrity, the cc1 frontend should utilize a vector-based design. In this model, all AST nodes of a particular type are stored in a contiguous Vec<T>. Instead of pointers, nodes refer to one another using "handles"—integer-based indices into the vectors.Advantages of Handle-Based Vectors:Cache Locality: Contiguous memory ensures that when the compiler traverses a block of statements, the relevant data is likely already in the CPU's L1/L2 cache.Memory Efficiency: Integer indices (e.g., u32) are smaller than 64-bit pointers, reducing the overall memory footprint of the AST.Ownership Clarity: Rust's borrow checker is easier to satisfy when using indices into a central Context rather than managing complex graphs of smart pointers.Parallelism: Storing data in vectors facilitates the "agent team" approach where different passes can operate on subsets of data without competing for heap locks.Arena Allocation with BumpaloFor ephemeral data created during specific translation phases, the compiler should employ arena allocation. Using the bumpalo crate allows the compiler to allocate memory by simply bumping a pointer within a pre-allocated block. When a phase (such as parsing a single function) is complete, the entire arena is dropped at once, eliminating the overhead of individual free() or Drop calls. This is a standard practice in production-grade compilers like rustc and LLVM.Integrating ft_lex and ft_yaccThe compiler utilizes custom-built ft_lex and ft_yacc tools, which must be integrated into the Rust build process using a build.rs script. The lexer generates a stream of Token structures, each containing a Span (the handle to the original source location) and a TokenKind. The parser, utilizing an LALR(1) or SLR(1) algorithm, consumes these tokens to build the handle-based AST.Preprocessor Subsystem and MetaprogrammingThe preprocessor is a critical component of the C89 toolchain, responsible for translation phases 1 through 4. It must replace the functionality of clang -E and provide a clean input for the main compiler.Macro Expansion AlgorithmThe macro engine must distinguish between object-like macros and function-like macros. The expansion process follows a strict sequence:Identification: The preprocessor identifies a macro name in the token stream.Argument Identification: For function-like macros, arguments are isolated, respecting nested parentheses and commas.Stringification (#): If an argument is preceded by the # operator, it is converted into a string literal.Concatenation (##): Tokens separated by ## are merged into a single token.Expansion and Rescanning: Arguments are expanded, then substituted into the replacement list. The resulting list is rescanned for further macro names. To prevent infinite recursion, the name of the macro currently being expanded is not replaced during the rescan.File Inclusion and Conditional LogicThe preprocessor must manage the #include search path, looking for <header.h> in system directories and "header.h" in the local directory. Conditional inclusion directives (#if, #ifdef, #ifndef, #elif, #else, #endif) allow for platform-specific code and include guards. These require an expression evaluator that supports the defined() operator and basic arithmetic.Middle-end: SSA Transformation and LLVM IntegrationThe bridge between the high-level C AST and target assembly is the LLVM Intermediate Representation (IR). The cc1 program must generate LLVM IR that is semantically equivalent to the C source while providing opportunities for LLVM's optimization passes.Static Single Assignment (SSA) ConstructionModern compilers typically lower the AST into an SSA-based IR. This process is effectively managed in two steps:Alloca-based Lowering: The compiler initially emits alloca instructions for all local variables, performing simple load and store operations for every variable access.SSA Promotion (mem2reg): A transformation pass, inspired by LLVM's mem2reg, promotes these stack-allocated variables to virtual registers, inserting Phi nodes where control flow paths merge.This architecture separates the concern of C semantics from the complexities of SSA management, resulting in cleaner and more maintainable code.Target Triple and Datalayout SpecificationThe generated LLVM IR must include metadata specifying the target environment. This ensures that the backend tools (llc, as) correctly handle calling conventions and memory layout.i386 Target Triple: i386-pc-linux-gnu x86_64 Target Triple: x86_64-pc-linux-gnu i386 Datalayout: Specifies 32-bit pointers and 4-byte alignment for doubles.x86_64 Datalayout: Specifies 64-bit pointers and 8-byte alignment for doubles.Backend Architecture and Register AllocationThe backend is responsible for lowering the IR into machine-specific instructions. While the mandatory part of the project relies on LLVM's llc, an original design requires a trait-based abstraction to support multiple architectures efficiently.Shared Logic and Architecture TraitsTo avoid code duplication, the backend should use a central ArchCodegen trait. This trait defines methods for emitting common operations (e.g., emit_move, emit_add), while architecture-specific modules implement these methods for i386 and x86_64.Common tasks like function call ABI classification—identifying which arguments go in registers (%rdi, %rsi, etc. on x86_64) and which go on the stack—can be implemented as default trait methods.Linear Scan Register AllocationEfficient register use is achieved through a linear scan allocator. This allocator analyzes variable liveness intervals and assigns them to available physical registers. The design must respect the distinction between caller-saved (scratch) and callee-saved (preserved) registers as defined by the System V ABI.Register Categoryx86_64 ExamplesUsage ConstraintCaller-Savedrax, rcx, rdx, rsi, rdi, r8–r11Not preserved across calls; ideal for short-lived values.Callee-Savedrbx, rsp, rbp, r12–r15Must be saved/restored by the function; used for values spanning calls.Debugging Infrastructure: The -g Flag and DWARF MetadataAdding support for the -g flag requires the compiler to emit detailed LLVM metadata that maps the generated IR back to the source code. This allows gdb to provide an interactive debugging experience.LLVM DIBuilder and Metadata NodesThe implementation utilizes the DIBuilder API (often accessible via the inkwell crate in Rust) to construct the DWARF metadata tree.Key Metadata Entries:DICompileUnit: The root node identifying the source language (C89), the producer, and the compilation flags.DIFile: Tracks the filename and directory of each source file.DISubprogram: Describes function metadata, including scope, linkage name, and line numbers.DILocalVariable: Maps registers or stack slots to local C variables.DILocation: An instruction-level attachment that links specific IR instructions to a file, line, and column.One technical challenge is the handling of recursive data types (e.g., struct list { struct list *next; }). The compiler must create "type stubs" and cache them to avoid infinite recursion during DWARF generation.Engineering Lifecycle: Git Flow and Milestone ManagementDeveloping a full-scale C compiler requires a disciplined project management approach.
